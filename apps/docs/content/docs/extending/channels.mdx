title: Conversation channels
description: Connect a Discord, Telegram, or GitHub conversation to a Happier session or automation, so people who do not use Happier can still talk to your agents.
---

A channel connects a conversation somewhere else — a Discord channel, a
Telegram chat, a GitHub issue or pull request — to a session or an automation
on your machine. Messages arrive as input, replies go back out, and the people
on the other end never install anything.

<Callout type="warn">
  Conversation channels are part of the current 0.3 Developer Preview. The
  source and bundled providers are present, but loaded-platform and authenticated
  provider journeys are still release gates rather than stable-release claims.
</Callout>

The current 0.3 source bundles **Discord**, **Telegram**, and **GitHub**
providers. Providers are a contribution point
rather than a fixed list, so a trusted installed plugin receives the same public
contract and can add another.

## The two halves

Channels separates *who you are connected to* from *what that connection drives*,
and it is worth holding those apart because they are configured separately and
can change independently.

**A connection** is the link to one conversation at a provider. It has its own
lifecycle: you create it, prepare it, enable or disable it, transfer it to
another machine, and eventually delete it.

**A binding** points a connection at a target — a session or an automation.
Bindings are enabled and disabled on their own, and a binding's target can be
**rotated** without tearing down the connection underneath. That is the move
when a session ends and you want the same Discord channel driving the next one.

## Getting connected

Credentials do not live in the channel setup form. Every provider binds to a
**Connected Account** holding its credential, and the setup action asks you to
*select* one — Telegram's own field description says bot tokens are never entered
there. So the order is: create the Connected Account first, then point the
channel at it.

| Provider | Credential purpose | How it reaches the provider |
| --- | --- | --- |
| Discord | `discord-bot-credential` | Discord REST plus a persistent gateway worker |
| Telegram | `telegram-bot-credential` | The Telegram bot API |
| GitHub | `github-connected-account` | The GitHub REST API over checkpointed polling |

Each provider also checks provider-side permissions at setup, so a credential
that authenticates but cannot actually reach the conversation is refused there
rather than at the first silent failure:

- **Discord** requires the application's privileged **Message Content
  Intent** to be enabled — setup reads the application flags and fails closed
  when it cannot confirm them — and the bot invited to the server with
  **View Channels**, **Send Messages** (or **Send Messages in Threads** for a
  thread), and **Read Message History**. Setup computes the bot's effective
  permissions at the exact destination, names any missing permission, and its
  guidance links an invite carrying exactly those permissions.
- **Telegram** reads the bot identity from the token. A shared conversation is
  a group or supergroup, and you point setup at it by its public @username —
  broadcast channels are not supported. A bot in a shared group also needs
  BotFather **Group Privacy** disabled — setup observes whether the bot may
  read all group messages, and every later connection test restates the
  *current* capability, so flipping privacy back on after setup surfaces on
  the next test instead of silently narrowing what the channel receives.
- **GitHub** verifies the selected repository against the credential and then
  exercises the exact issue-comment collection the channel polls, so a token
  with repository access but without the **Issues** permission is refused at
  connection time. Replies post as issue comments, so the credential needs
  write access to that same collection.

Connecting a Discord or Telegram conversation runs a **pairing challenge** that
you then finalize —
or cancel. You choose the conversation to connect; whoever claims it proves who
they are by sending the challenge token to the bot in a **private message**, and
is answered there once the request has been recorded. That keeps the token out
of a group everyone can read while still connecting the group you picked.
Pairing exists so that connecting a conversation is something somebody has to
agree to, rather than something you can do to a channel from the outside.

### GitHub repositories

The GitHub provider ships inside the bundled GitHub hosting provider plugin and
connects one repository at a time: setup verifies the selected repository
against your GitHub Connected Account credential. Each conversation is a single
issue or pull request in that repository — you point a binding at it by number.
Comments on that issue or pull request arrive as channel messages, and replies
are posted back as comments on it. The provider splits a reply across several
comments once it exceeds Happier's provider safety ceiling of 65,536 UTF-8
bytes per comment. GitHub has no webhook delivery in this preview: inbound
messages arrive through checkpointed polling, so a connected machine needs to
wake up for the poll to advance.

### The history baseline

When a connection starts, Happier does not swallow everything said in that
conversation before you arrived. It offers a **history baseline** for you to
accept, and ingestion starts from there. This is the setting people wish they
had thought about after connecting a busy channel, so it is asked up front.

## When something is blocked

Channels are conversations with other people's infrastructure, so parts of the
model are about failure rather than success:

- **Blocked ingress** can be retried, rather than the message being lost.
- **A blocked poll** can be retried the same way.
- **Ambiguous delivery** — where Happier cannot tell whether an outbound
  message reached the conversation — is resolved explicitly instead of
  guessed: you record it as accepted or discard it. Happier never resends an
  ambiguous delivery on its own.

What Happier keeps is bounded to what recovery still needs. Inbound message
content is retained while its admission obligations are live, then reduced to
a compact replay-evidence shell and deleted once the transport's replay window
has passed. An outbound delivery that reaches a terminal state is kept for a
thirty-day recovery window so a failure can be resolved; an ambiguous partial
delivery keeps only a fingerprint of its content but stays visible until you
resolve it, and delivered content is deleted when its window elapses.

Two collections sync with your account: the channel state itself, and the
delivery records. Between them they are what lets a retry know what already went
out.

## Channels and automations

A binding can target an automation rather than a session. When a message is
admitted through that binding, Happier invokes a Conversation-origin Run for
the selected automation; the automation's own definition remains independent
of the conversation binding. Together that is: someone comments on the connected
GitHub issue or posts in a Discord channel, a Run starts on your machine, and
the result is delivered back into the conversation.

For a verified automation that starts or continues a Session, the binding can
deliver the final result or deliver no result. Execution-run automations support
no result delivery through a channel. Happier rejects an unsupported pairing or
binding before saving it.

Final-result delivery uses the same Conversation result envelope, encrypted
handoff, and delivery custody as the Session itself. Channels does not keep a
second result store or plaintext fallback, and it does not impose a separate
Channels-specific result-size ceiling. Failed and cancelled Runs settle the same
handoff truthfully instead of leaving a conversation waiting forever.

## Approvals and questions

For a Session binding, the owner can allow people in the connected conversation
to approve or deny the Agent's current permission request. Happier sends the
Agent's bounded request summary to the conversation, and `/allow <request-id>`
or `/deny <request-id>` goes back through the Session's ordinary permission
handler. The binding can allow one request at a time or permission for the
Session; Channels does not create another grant model.

Agent questions use that same mediation path but are not permission grants. A
question message includes the real prompt, required/optional state, selection
mode, and available choices. Reply once with the shown request id and indexed
answers:

```text
/answer <request-id> [{"questionIndex":0,"values":["Choice label"]}]
```

Questions remain answerable when permission approvals are disabled. Happier
still enforces the binding's Account, participant, Session, and request
currentness before accepting an answer.
