This page documents how Happier integrates with **OpenCode** and what matters for day-to-day use.

## Requirements

- OpenCode CLI installed on your machine.
- Binary available on `PATH` (or set `HAPPIER_OPENCODE_PATH`).

Happier also recognises the OpenCode **V2 beta** executable, `opencode2`. See
[OpenCode V2 beta](#opencode-v2-beta).

## Install OpenCode

If you use Happier's legacy-named `provider` installer, you can install OpenCode from the CLI:

```bash
happier install provider opencode
opencode --version
```

Or install manually:

```bash
curl -fsSL https://opencode.ai/install | bash
opencode --version
```

On Windows, OpenCode also supports native installs such as:

```bash
npm install -g opencode-ai
opencode --version
```

If Happier offers to run OpenCode’s vendor install recipe for you, it requires explicit confirmation before executing vendor install commands.

## Local authentication in Happier

OpenCode supports machine-local auth management in:

- **Settings → Agents → OpenCode**

From there you can:

- check whether OpenCode is authenticated on the selected machine
- open `opencode auth login` directly inside Happier
- refresh the auth state with **Check now**

Happier reads OpenCode’s local auth state through the CLI’s own auth listing flow when available.

For the shared user guide, see [Agent authentication](/agents/provider-authentication).

## How Happier runs OpenCode

OpenCode has two runtime paths in Happier:

- **Server-native (default)**: Happier talks to the OpenCode server/session APIs directly. This is the normal path for new OpenCode sessions in Happier.
- **ACP (legacy fallback)**: still available when you explicitly switch OpenCode to ACP mode.

For most users, the important part is:

- new OpenCode sessions default to the **server-native** backend,
- Happier can keep the same OpenCode session visible in both the app and the terminal,
- attaching later should use `happier attach <session-id>`, not a raw vendor attach command.

By default, Happier uses a **managed local OpenCode server** on the machine and reuses it across sessions. Advanced users can set an explicit OpenCode server URL in settings; when you do that, Happier will keep using that explicit server for the session.

## OpenCode V2 beta

OpenCode's V2 beta ships as a separate executable named `opencode2`. Happier recognises it through
the same server-native backend — there is no separate OpenCode integration to enable.

Happier speaks the standalone V2 `/api/*` contract through the same server-native backend: creating
and resuming sessions, prompting, model and variant selection, cancelling, compacting, reading the
transcript, answering permissions and questions, listing skills, and listing providers and models.
A short list of features has no V2 route at all — see
[What V2 does not support yet](#what-v2-does-not-support-yet).

<Callout type="warn">
  Happier's V2 support is built against OpenCode's published V2 protocol, but it has **not yet been
  exercised against a live `opencode2` server**. Treat it as untested in practice rather than
  unsupported, and report anything that misbehaves.
</Callout>

**Which executable Happier runs.** Happier looks for `opencode` first and `opencode2` second. So:

- only `opencode` installed → Happier runs the stable CLI;
- only `opencode2` installed → Happier runs the beta;
- both installed → Happier keeps running the stable `opencode`, so a beta install never silently
  replaces your working setup.

**Starting the server.** Happier waits for the server it started to report itself ready, and it
asks on the route that binary actually answers: `/global/health` for `opencode`, `/api/health` for
`opencode2`. It reads this from the executable it resolved, not from any setting.

**Which routes Happier then uses.** The same fact decides that too. When Happier started an
`opencode2` server itself, that session uses the V2 request routes with no configuration. A server
you run yourself and point Happier at is different: Happier cannot see which binary you started, so
it keeps the stable routes unless you ask for V2 in the session's launch environment:

```bash
HAPPIER_OPENCODE_SERVER_DIALECT=v2
```

Whenever V2 is asked for — by that opt-in or by Happier having spawned `opencode2` — Happier
confirms it once per session, before the first request:

- the server answers `/global/health` → it is a stable server (stable builds serve `/api/health`
  too, so the legacy route is what tells them apart) and Happier uses the stable routes;
- only `/api/health` answers, with `{ "healthy": true }` → Happier uses the V2 routes and the V2
  event stream;
- neither answers, or the answer is unusable → Happier keeps the stable routes rather than guessing.

The resolved choice — requested and actual, plus the health route and status that decided it — is
recorded in the OpenCode server log for that session, alongside the readiness route and the
executable it came from.

**The V2 event stream is live, not replayable.** The server sends no event ids and offers no
backlog, so Happier receives events only from the moment it is connected. If the connection drops,
Happier reconnects and subscribes again from that point; anything the server published while no
connection was open is not delivered afterwards. The stable transport behaves the same way.

### What V2 does not support yet

These are gaps in OpenCode's V2 protocol, not settings you can turn on. Each one fails on its own
and is recorded in the OpenCode server log for that session; none of them stops you prompting.

- **Happier's MCP tools, including automatic title updates.** V2 has no route for registering an
  MCP server at runtime, so Happier cannot attach its tool bridge to a V2 session. This is the one
  case where Happier deliberately does *not* fail the turn — the capability is absent rather than
  refused, so the session keeps working without Happier's own tools.
- **Forking a session.** V2 declares no fork route, so forking fails with that reason rather than
  quietly starting an unrelated session.
- **The native to-do work state.** V2 publishes `todo.updated` events but offers no route to read
  the list back, so the to-do panel stays empty.
- **Per-prompt configuration overrides**, and OpenCode's global configuration read that Happier uses
  to guess a default model. Model and variant selection themselves do work: Happier sets them on the
  session's own V2 model route immediately before the prompt.
- **Connected accounts are unproven on the V2 transport.** When you sign OpenCode in through a
  Happier connected account, Happier installs a small OpenCode plugin that supplies the provider
  credential. That plugin uses OpenCode's V1 plugin `auth` hook, which has no counterpart in
  OpenCode's V2 plugin API. Happier records a warning in the OpenCode server log for such a session.
  Use a provider API key or OpenCode's own `opencode auth login` if the connected account does not
  work.
- OpenCode's V2-only configuration keys (for example the V2 `permissions` block) are rejected by
  the stable `opencode` binary. Keep V2-only configuration for machines running `opencode2`.
- **Live turn state for a linked session you are not watching.** When Happier reconciles a linked
  external session in the background it reads the stable server's session-status route, which a V2
  server does not serve. Those checks simply fail rather than reporting a wrong state, and opening the
  session reads its transcript normally.
- There is no Settings control for the manual opt-in yet; it is a launch-environment value while the
  transport is unproven against a live `opencode2` server.

Browsing external OpenCode sessions does work on a beta-only machine. When Happier starts its own
server for that surface, it reads the resolved executable first — the same way a session does — so an
`opencode2` server is checked for readiness and then listed, opened and paged over the V2 routes. A
server **you** started and pointed Happier at is always read over the stable routes, because Happier
resolved no executable for it and the `/api` surface alone does not prove which engine is behind it.

## Start OpenCode from a terminal

```bash
happier opencode
```

When you start OpenCode this way:

- the session appears in Happier as a normal session,
- the terminal starts in **local/shared control**,
- the Happier app can still see the same transcript and send messages into the same OpenCode session,
- messages typed directly into the OpenCode TUI also show up in Happier.

This is useful when you want the Agent TUI first, but still want the app to stay attached to the same session.

### Detach from the app

If the session is locally attached, the session header in Happier shows **Detach terminal**.

Using it:

- switches the session back to **remote** control,
- keeps the same session id and transcript,
- closes the attached OpenCode TUI while the Happier session keeps running.

You can later run `happier attach <session-id>` from a terminal on the same machine to get back into the OpenCode TUI.

## Start OpenCode from the app

If you start a new OpenCode session from the Happier app:

- Happier starts it in **remote/server-only** mode in the background,
- the app can use the session immediately,
- no terminal needs to be open yet.

Later, on the same machine, you can attach a terminal to that live session with:

```bash
happier attach <session-id>
```

After attaching:

- the session switches into **local/shared control**,
- the terminal shows the OpenCode TUI,
- the app still stays connected to the same session and transcript.

This is the main “start in the app, continue in the terminal” workflow for OpenCode.

## Local vs remote control in OpenCode

OpenCode uses **shared local control** in Happier.

That means:

- **Remote mode**: Happier drives OpenCode in the background and you use the app/web UI
- **Local mode**: you use the OpenCode TUI in a terminal
- the transcript stays shared in both modes
- the session stays writable from the app even when a terminal is attached
- app messages do not need the pending-queue handoff used by exclusive local-control paths

In practice, you can:

- send a message from the app and watch it appear in the attached OpenCode TUI,
- send a message from the OpenCode TUI and see it appear in Happier,
- detach and reattach without starting a new session.

For the full switching workflow, see [Features → Attach to a running session](/sessions/attach-to-session).

## Authentication (connected services)

OpenCode can reuse connected services profiles when spawned by Happier (for example):

- `openai-codex` (subscription OAuth) or `openai` (API key) for OpenAI-backed usage
- `claude-subscription` setup-token profiles or `anthropic` (API key) for Anthropic-backed usage

If multiple compatible profiles exist, Happier will let you pick one when starting a new session.

OpenCode accepts `claude-subscription` only for setup-token profiles. Claude subscription OAuth profiles are hidden from OpenCode selection and require Claude itself.

See: [Connected services](/accounts/connected-services)

## Session handoff

OpenCode supports Happier session handoff between machines.

This is a natural fit for OpenCode because Happier can move the same Happier session while preserving OpenCode continuity on the new machine.

Use it when you want to:

- move a live OpenCode session from one machine to another
- keep the same Happier session id
- continue the same work from the target machine

Connected services can help here too, especially when the target machine should reuse account-managed credentials instead of depending only on a local machine login state.

See:

- [Session handoff](/sessions/session-handoff)
- [Connected services](/accounts/connected-services)

## Permissions, modes, and models

Happier uses the same Agent-agnostic permission picker for OpenCode as it does for other Agents.

Important OpenCode notes:

- permission intent is chosen in Happier,
- Happier maps that intent to the closest OpenCode session permission ruleset,
- some OpenCode behavior still depends on the installed OpenCode runtime.

OpenCode can also expose Agent-native session modes and model choices. When those are available, Happier surfaces them in the session UI.

For the full user guide, see:

- [Model and engine selection](/agents/model-and-engine-selection)
- [Permissions](/sessions/permissions)

## Notes

- Resume availability is session-specific in Happier: the session must have valid OpenCode resume metadata, and your current backend/settings must allow resume.
- Attach availability is also session-specific: the session must have the metadata/context Happier needs to reopen that OpenCode session locally.
- Model, mode, and permission behavior can still vary by installed OpenCode runtime.
- Tool events are normalized into Happier’s canonical tool timeline.
- For OpenCode reattach flows, the supported command is `happier attach <session-id>`.

## Troubleshooting

If OpenCode is not detected:

1. Verify `opencode --version` works.
2. Restart Happier.
3. Set `HAPPIER_OPENCODE_PATH` if your binary is not in PATH.

### The session is visible in the app but I want the TUI again

Use:

```bash
happier attach <session-id>
```

Do this on the same machine and against the same Happier account/server profile that owns the session.

### The terminal is open but no longer accepts prompts

This usually means the session was detached back to remote mode from Happier. Reattach with `happier attach <session-id>` from a terminal on the same machine.
