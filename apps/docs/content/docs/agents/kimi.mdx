Happier runs the locally installed Kimi Code CLI through `kimi acp` for managed
sessions and execution runs. Kimi remains experimental upstream, so verify its
behavior on the version installed on your Agent machine.

## Requirements

Install the current Kimi Code CLI, ensure `kimi` is on `PATH` (or set
`HAPPIER_KIMI_PATH`), then sign in:

```bash
happier install provider kimi
kimi login
```

Or install it yourself (macOS / Linux):

```bash
curl -LsSf https://code.kimi.com/kimi-code/install.sh | bash
kimi --version
```

Windows (PowerShell):

```powershell
Invoke-RestMethod https://code.kimi.com/kimi-code/install.ps1 | Invoke-Expression
kimi --version
```

You can launch the same login flow from **Settings → Agents → Kimi**. Happier
detects the system CLI; it does not run a package manager on your behalf.
Auth-status detection for Kimi is currently conservative, so Happier may still
show **Unknown** even though the login flow is available.

## Sessions and controls

Start a session with `happier kimi`. Happier projects the models and agent
modes advertised by Kimi's ACP server instead of keeping a separate model
list. New sessions, resume, cancellation, and follow-up prompts use the
shared ACP lifecycle. Happier does not translate modes into top-level Kimi
flags. When a session ends, Happier releases Kimi's own session through the
shared lifecycle if that connection advertised session close.

If Kimi's ACP server advertises session listing, its sessions appear in the
“resume in Happier” picker, and when the same connection also advertises
session deletion each listed row offers a confirmed delete. That deletes
Kimi's own session record; your Happier session and its history stay. Nothing
disappears from the list until Kimi confirms the deletion, and a failure leaves
the row in place so you can retry.

Kimi receives selected Happier tools as per-session ACP MCP descriptors,
including the stdio, HTTP, and SSE transports Kimi supports. Project and user
MCP configuration remains owned by Kimi.

Update an existing current installation with:

```bash
kimi upgrade
```

## Interactive terminal

The terminal action launches ordinary `kimi` through Happier's existing
terminal host. It is an auxiliary interactive surface; it does not create a
second Happier session runtime or promise that terminal and ACP session IDs
match.

## Troubleshooting

- Run `kimi --version` on the Agent machine if Kimi is not detected.
- Run `kimi login` again if Kimi reports an authentication error.
- If a model or mode is missing, check what the installed `kimi acp`
  advertises.

### Coming from the retired Python `kimi-cli`

Happier resolves only the `kimi` executable that current Kimi Code installs, so
a separately installed legacy `kimi-cli` binary is never launched as if it were
Kimi Code. Existing Happier sessions recorded under the old name keep working,
because `kimi-cli` is still accepted as a session alias.

What a connected runtime may do is decided from the capabilities that exact ACP
connection negotiates when Happier connects — never from a version number,
which is unreliable here because some retired `kimi-cli` releases sort above
current Kimi Code releases. A runtime that does not negotiate resume cannot be
resumed, and Happier reports that instead of silently starting a fresh
conversation.

If you are still on the retired CLI, install current Kimi Code and run the
vendor migration yourself:

```bash
kimi migrate
```

Happier never runs migration automatically. `HAPPIER_KIMI_PATH` only chooses
which executable is launched; it grants no capability the connected runtime
does not negotiate.
