---
title: Run background work
description: Register daemon-occurrence background work without adding a second lifecycle owner.
---

Use `backgroundServices` for daemon/machine work that is not an action,
Session turn, Agent factory, or event handler. A `definePlugin` declaration
pairs a cold row with one runner; the runner registration itself is generated,
so there is no separate registration call to maintain.

```ts
backgroundServices: [{
  declaration: { id: 'catalog-refresh', title: 'Refresh catalog' },
  async runner(context) {
    context.signal.throwIfAborted();
    // Do bounded work with context.services.
  },
}],
```

The host starts the runner after occurrence commit and retires it on
replacement, disable/uninstall, or daemon shutdown. Do not use event activation
as a background scheduler, and do not build a runner-owned polling loop to
imitate one: use the Events service for event semantics, not for plugin-owned
background lifecycle. Honor `context.signal`, let failures surface as
diagnostics, and avoid a plugin-owned watcher, timer registry, or service
lifecycle cache.
