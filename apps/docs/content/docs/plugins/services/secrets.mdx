---
title: Secrets service
description: Store plugin-owned secrets without exposing values through projection.
---

Use `context.services.secrets` for plugin-owned secret values.

## Availability

Available in the current source contract. The [capability matrix](/plugins/manifest/availability)
records loaded-platform and release evidence separately from source
availability. The public external-author reference below provides maintained
source-shape coverage for the service.

## Declare the secret first

The service resolves only declared identifiers. Declare each plugin-owned secret
in the manifest, either as a `secret` Settings field or through the top-level
`secrets` list:

```ts
secrets: [{ id: 'document-review-webhook-token' }],
```

An undeclared identifier is rejected with `plugin_secret_undeclared`; it is not
created on first write. Omitting `custody` selects Account custody.

## Operations

- `status(id)` reports configured, missing, denied, or unavailable without returning the value.
- `get(id, options)` reads a value when the host grants access.
- `set(id, value, options)` stores a value.
- `delete(id, options)` removes a value.

Mutation results carry a revision. Use `expectedRevision` when a caller must reject a conflicting update.

## Rules

- Do not store tokens in the manifest, settings, plugin storage, or UI descriptors.
- Do not log or emit secret values.
- Ask for a secret only at the point it is needed and provide a user-readable reason.
- Use `context.services.connectedAccounts.materialize(purpose, request)` for host-managed account credentials instead of copying them into plugin storage.

Saved Secrets belong to the host catalog, not to the plugin secret service. In current development
source that catalog can resolve personal and shared Saved Secret references for an admitted host
operation. An installed external plugin and a bundled plugin receive the same declared public
service and host-policy decision; neither can enumerate the Account's secret store or turn a Saved
Secret reference into unrestricted read authority. Shared Saved Secrets remain a development-only
product and must not be advertised until their complete consumer and live validation gates pass.

## Worked example

The public external-author reference `packages/plugin-sdk/examples/action-contract-producer`
declares one plugin secret and rotates it from an Action: it reads `status` for the incumbent
revision, passes that revision as `expectedRevision` so a concurrent rotation
loses instead of overwriting, reads the value back at the point of use with a
reason, and returns only the state and revision.
