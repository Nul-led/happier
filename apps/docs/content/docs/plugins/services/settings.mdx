---
title: Settings service
description: Read and update plugin settings declared by manifest descriptors.
---

Plugin settings are available through `context.services.settings` in invocation
and Agent runtime contexts.

## Descriptor-first settings

Settings fields should be declared in the manifest through the single
`contributes.settings[]` family. Set `target` to `{ kind: 'plugin' }` for
plugin-local settings or `{ kind: 'agent', agent: '<agent-ref>' }` for an
Agent contribution.

## Runtime access

Plugin code can:

- read all settings
- read one setting by key
- set a setting
- subscribe to changes
- describe fields
- project a settings form

Choose the declaration scope before reading, writing, or watching settings.
There is no unscoped settings operation and no merged Account/daemon view:

```ts
const accountSettings = context.services.settings.forScope({ kind: 'account' });
const watcher = accountSettings.watch((change) => {
  // `change.scope` is always `{ kind: 'account' }` here.
});
```

Use `{ kind: 'daemon' }` only for fields declared with daemon scope.

A non-secret field id must be unique within its scope, so the same id may name
one Account field and one daemon field. Secret ids share one plugin-wide
namespace: a secret field or a top-level `secrets` entry cannot reuse any other
Settings id.
`ScopedSettingsService.watch(listener)` returns a `Disposable`. Dispose it when
its owning activation or runtime stops. A watcher is a live observation, not a
history API.

## Account changes during a write

In the current development source, an Account-scoped Settings operation keeps
the same Account context for its read, conditional write, and any readback.
Switching Accounts cannot redirect an in-progress write to the new Account.

After a write has been dispatched, a valid acknowledgement still settles that
operation; retirement does not turn an applied write into a cancellation. The
host does not publish its retired Settings snapshot into the new Account's
view. A lost or invalid acknowledgement remains an unknown outcome, so reread
the original Account's settings before deciding whether another write is safe.

The same settlement rule covers Account-secret bindings. When the initiating
Account has retired or its Settings projection has advanced, a successful
secret write can return its acknowledged revision without a snapshot. A known
conflict stays a conflict even when no current snapshot can be disclosed.

## Design rules

- Keep display metadata in descriptors.
- Keep secret values in `context.services.secrets`, not settings.
- Preserve unknown plugin-owned settings keys unless a migration intentionally changes them.
- Do not add owner-specific branches in generic settings UI code; use the
  canonical descriptor target.
