> **Availability:** `happier home create` is available in the 0.3 development/preview line. Stable 0.2 supports the generic Relay runtime paths below, but not Personal Home creation.

For a personal deployment, start with the explicit Home command:

```bash
happier home create
happier home create --ssh user@host
```

Both forms install or reuse the same managed Happier server runtime, then run the atomic Personal Home bootstrap. The local form keeps the Home on this computer; the SSH form creates it on the trusted remote host. Its HTTP listener can remain loopback-only because the server publishes an Iroh descriptor for Home reachability. Public ingress is optional.

Personal Home data is plaintext at rest on its host. Use a computer or hosting provider you trust. When creation finishes, use `happier home pair-device` to start a new device-link session or `happier home link-account` to make the Home discoverable through your signed-in Account Service.

Happier also supports three **operator/runtime** self-host shapes:

1) a **managed install** (service + config) driven by `happier relay host …`
2) a **Docker image** that bakes verified server-runtime + UI-web artifacts into the image
3) a **runner** that downloads/verifies artifacts on startup and starts the server process (`@happier-dev/relay-server`)

They are complementary, but they are not the same thing.

For a complete “what updates automatically vs manually” matrix across all shipped assets (desktop/mobile/web, CLI installers, Docker images, and runners), see: [Updates](/releases/updates).

## Option A: Managed generic/operator install

Use `happier relay host install` when you want:

- the server installed as a **managed service** (user/system mode)
- a repeatable **install-or-update** command for your selected channel

This command manages the generic server runtime. It does not create an account, change signup policy, enroll a device, or convert an existing runtime into a Personal Home.

First, install the Happier CLI: see [CLI install](/apps/cli).

Install locally:

```bash
happier relay host install --mode system
```

Local bind options:

```bash
happier relay host install --lan
happier relay host install --expose
happier relay host install --host 192.168.1.25
```

Use `--lan` to bind to a private LAN address, `--expose` to bind to all interfaces, or `--host <ip>` to bind to one local address. These flags are local-install-only; they do not apply to SSH installs.

Install remotely over SSH:

```bash
happier relay host install --ssh user@host --mode system
```

After install, you manage it with:

```bash
happier relay host status
happier relay host start
happier relay host stop
happier relay host restart
```

To update, rerun `happier relay host install` (it installs or updates to the latest version in that channel).

### Auth compatibility during this update

Keep `HANDY_MASTER_SECRET` unchanged. Persistent auth tokens and encrypted server data are both derived from it, so rotating it is not an auth-repair procedure and can make existing data unreadable.

When updating from a preview relay that used Bun 1.3.5, stop or drain every old relay process before starting the new version. Do not run old and new relay binaries behind the same endpoint during the rollout: the corrected version accepts both the canonical historical key and the Bun-retry key, but an old process may reject tokens newly issued with the canonical key. A complete restart removes that mixed-version direction while preserving existing sessions.

### Account lifecycle upgrade boundary (development)

The 0.3 development Account lifecycle migration makes Account status authoritative. After it activates, do not start an older server that does not enforce that status, including alongside the new server: it could admit a Disabled or Retired Account. This server boundary does not require every client to update.

Before this upgrade, stop all old API and worker instances that share the database. Update the Happier installer first. The managed updater refuses automatic restoration of the previous server when the lifecycle migration is applied or its applied state cannot be determined. Keep the candidate stopped after a failed upgrade and recover forward with a status-aware server; preserve the database and the updater's recovery files.

Docker, runner, and manually supervised deployments must enforce the same stop-and-upgrade procedure. An old binary cannot detect this new contract and may still start; manual old-binary startup is unsupported and unsafe. Disabling Teams does not make that rollback safe, because Account lifecycle enforcement is independent of Teams availability.

### Personal Home data: uninstall, erase, backup

When the managed runtime on this computer runs your Personal Home, its lifecycle commands are data-safe by design. `happier relay host uninstall` removes the service registration, the runtime binaries, and the logs — and deliberately preserves the Home's SQLite database, public and private files, master secret, configuration, and local backups. Reinstalling finds the same Home with its sessions and trusted devices intact.

Deleting that data is a separate, explicit step: `happier home erase`. It shows the affected Home, exact owner-resolved paths, and a bounded size estimate while the Home still runs, then requires one explicit confirmation (`--yes` in non-interactive runs). Large or unreadable trees can have an unknown size. It rechecks the confirmed facts before stopping the Home and validating every deletion target. A failure before deletion attempts to restart a previously running Home; a partial deletion leaves it stopped. If you want a recovery copy, create and verify an external backup separately first; erase never creates one implicitly. It never runs as a side effect of uninstall, logout, or profile removal.

In the 0.3 development implementation, retrying a failed Personal Home runtime update finishes the already selected candidate when its installation was recorded as complete. It does not install a different requested version or restore older Home data. If interruption happened before candidate selection was complete, the Home stays quarantined and reports that the incomplete candidate needs inspection. Preserve its data and recovery files; repeatedly requesting a different version does not resolve that ambiguity.

The CLI also owns complete-Home backups: `happier home backup` creates and verifies a plaintext archive of the database, files, master secret, and Home configuration, `happier home verify-backup` re-checks any archive, and `happier home restore PATH` restores a verified archive with validation, forward-only migrations, and automatic rollback on failure. Each operation also accepts `--ssh user@host` to target the managed Personal Home on a trusted remote host; destructive approval remains bound to that host and Home's current facts. See [Personal Home data operations](/apps/cli) for the full command reference. A backup is plaintext and contains readable conversations, the Home master secret, and trusted-device state — store it somewhere you trust.

Two boundaries keep this distinct from the rest of Happier: standard relay and Happier Cloud behavior is unchanged, and end-to-end-encrypted Homes are never searched server-side. The Personal Home's transcript search is a local, rebuildable plaintext index (FTS5) served by this runtime. When that Home index is still indexing or unavailable, Search can use an otherwise eligible, explicitly selected daemon-memory source; if none is eligible, it reports the Home state instead of pretending there were no matches. E2EE and non-Personal-Home paths continue to use their existing eligible search source.

After installing a local Relay, you can save or activate the matching local Relay profile with:

```bash
happier relay add --local
happier relay use --local
happier relay set --local --use
```

Local Relay aliases default to the current CLI release channel. Pass `--local-channel stable|preview|dev` when you need a different installed lane.

This managed Relay runtime is separate from this computer's Happier background service. Installing the CLI or hosting a Relay does not automatically configure the background service for sessions; use `happier setup` for first-time computer setup and `happier doctor repair` to fix drift or broken state later.

## Option B: Docker image (recommended starting point)

The `happierdev/relay-server` image is built from the same signed server-runtime and UI-web release artifacts, but they are fetched and verified during the Docker image build. The running container starts the embedded `happier-server` binary directly.

This is ideal when:

- you run the server in **Docker**, Compose, Nomad, or Kubernetes
- you want image-pull based updates
- you do not want the container to download new application artifacts on every restart

See: [Docker](/self-hosting/docker).

## Option C: Runner (`@happier-dev/relay-server`)

The relay server package is a **server runner**:

- it fetches the server runtime by rolling tag (`server-stable` / `server-preview` / `server-dev`)
- verifies and extracts it into a cache
- optionally fetches the UI web bundle (`ui-web-stable` / `ui-web-preview` / `ui-web-dev`)
- sets `HAPPIER_SERVER_UI_DIR` (if UI is enabled)
- then starts the extracted `happier-server` binary

This is ideal when:

- you already have a process supervisor
- you want updates to happen on **restart** (no managed install / no scheduler)
- you do not want `hstack` installing services/timers/tasks on the host

Example (local runner):

```bash
npx --yes --package @happier-dev/relay-server happier-server --help
```

Important: because this is a runner, `happier relay host …` service controls do **not** apply to it.

## Metrics default note

The direct server binary defaults `METRICS_ENABLED=true`, but runtime-managed self-host surfaces currently write `METRICS_ENABLED=false` unless you override it explicitly. That keeps local multi-process and managed-service launches from colliding on the metrics port by default.

If you want metrics in a managed self-host/runtime launch:

```bash
METRICS_ENABLED=true
METRICS_PORT=9090
```

If multiple local processes may run at once, prefer distinct ports or `METRICS_PORT=0` per process.

For a production-style self-host deployment, use Prometheus and Grafana rather than scraping `/metrics` manually. The repo ships a Docker-friendly observability pack under `apps/server/observability/`; see [Observability](/self-hosting/observability).

## Choosing between them

- If you want a **service** and managed lifecycle → use **Option A**.
- If you want a self-contained container image → use **Option B**.
- If you already have a process manager and want artifact downloads on restart → use **Option C**.

If you’re unsure, start with Docker and switch to a managed install later.
