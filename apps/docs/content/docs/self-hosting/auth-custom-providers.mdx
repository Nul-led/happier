title: Custom auth providers
description: How authentication providers and methods compose in 0.3 development source, including extension points for enterprise forks.
---

In 0.3 development source, Happier composes built-in and deployment-configured
authentication providers through one catalog. This page is a contributor reference
for enterprise forks; it does not describe a released plugin API for authentication
providers.

Key idea:

- An auth mechanism is an **auth method**.
- A method can support multiple **actions** (for example: `login`, `provision`, `connect`).
- The server advertises methods centrally via `capabilities.auth.methods[]`.

## Provider composition (server)

Provider modules live under:

- `apps/server/sources/app/auth/providers/*`

`providerModules.ts` builds a deployment snapshot containing the built-in GitHub
module, valid OIDC modules, configuration errors, and an opaque runtime reference for
each included provider. It does not keep a live registry or provider cache. Invalid,
duplicate, or reserved OIDC entries are excluded without removing unrelated valid
providers.

The snapshot is composed in:

- `apps/server/sources/app/auth/providers/providerModules.ts`

Live OAuth, identity, eligibility, and profile-presentation lookups go through:

- `apps/server/sources/app/auth/providers/identityProviderCatalog.ts`

Each live lookup resolves the requested facet together with its runtime reference.
OAuth attempts retain that reference, so removing a provider or changing its
security-relevant configuration prevents an already-started attempt from completing
against a different runtime. The catalog resolves from current configuration for each
operation; there is no invalidation bus or static provider-instance cache.

The synchronous `/v1/features` projection cannot call the asynchronous catalog, so
`deploymentProviderFeatures.ts` projects from the same deployment snapshot. It owns
no separate provider instances or policy decisions.

Each module can contribute one or more **facets**:

- `oauth`: OAuth redirect/callback flow wiring (e.g. GitHub/OIDC)
- `identity`: identity linking + offboarding eligibility enforcement
- `auth`: provider status/capabilities surfaced under `capabilities.auth.providers`

Non-OAuth auth methods (like mTLS) are registered separately via the **auth-method registry**:

- `apps/server/sources/app/auth/methods/registry.ts`
- `apps/server/sources/app/auth/methods/modules/*`

## Adding a static provider module (enterprise fork)

Provider modules are the source-level extension point for OAuth-based identity
providers that cannot be expressed through OIDC deployment configuration.

1. Implement a `ProviderModule` with the `oauth`, `identity`, and `auth` facets its
   flow needs under `apps/server/sources/app/auth/providers/`.
2. Add it to `staticProviderModules` in
   `apps/server/sources/app/auth/providers/providerModules.ts`.
3. Add the matching client flow and presentation. Server registration alone does not
   create a usable sign-in experience.

The provider ID must not collide with another static provider, a core auth method, or
the compatibility `anonymous` method. Keep provider execution behind the identity
provider catalog so route behavior and feature advertising resolve from the same
composition.

## Adding a custom auth method (enterprise fork)

Auth methods are the right extension point for login mechanisms that are **not** the built-in key-challenge route and are **not** implemented via OAuth/OIDC config.

1. Create a new auth-method module, for example:
   - `apps/server/sources/app/auth/methods/modules/acmeAuthMethodModule.ts`

2. Implement an `AuthMethodModule`:
   - Types: `apps/server/sources/app/auth/methods/types.ts`
   - Reference implementation (mTLS): `apps/server/sources/app/auth/methods/modules/mtlsAuthMethodModule.ts`

3. Register the module by adding it to `staticAuthMethodModules` in:
   - `apps/server/sources/app/auth/methods/registry.ts`

After that:

- `authRoutes(...)` will register your login routes automatically.
- Boot-time lockout prevention uses the advertised `capabilities.auth.methods[]` actions; ensure your method reports at least one enabled `login`/`provision` action when correctly configured.
- `/v1/features` will advertise methods via `capabilities.auth.methods[]` so clients can render options without guessing.

## UI considerations

Adding a server login provider does not automatically add a UI login flow.

The built-in mTLS flow is implemented as:

- Web: `POST /v1/auth/mtls`
- Mobile handoff: `/v1/auth/mtls/start` → `/v1/auth/mtls/complete` → `POST /v1/auth/mtls/claim`

Enterprise forks can implement custom UI flows similarly while retaining the shared
auth-method registration and feature advertising from core.
